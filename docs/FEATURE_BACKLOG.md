## 建议 1：`move_paths` —— 移动/重命名没有安全版本（最该做）

### 缺口

- `delete_paths` 走**回收站**，可撤销，逐次审批。
- 但 `mv` / `move` / `ren` 全在 bash 名单里，**没有专用工具，也不可撤销**。

后果：用户说"把下载文件夹整理一下"或"把这批文件名里的日期改掉"，模型只能拼
bash 命令。一次 `mv` 手误就是文件丢失，而删除反而有保护。

这是**保护等级倒挂**：更常见的操作（移动）比更危险的操作（删除）更不安全。

### 做法

```
move_paths(moves: [{from, to}], dry_run: bool = true)
```

- 默认 `dry_run=True`：先返回"将会移动 A→B（12 项）"的清单，不改磁盘。
- 真正执行需 `dry_run=False`，走审批（复用 `delete_paths` 的逐次审批 + 子代理
  排除 + 定时禁止）。
- **可撤销**：每次移动写一条 `moves.jsonl`（from/to/ts），配 `undo_moves` 或
  `/undo-move <id>`。撤销就是把 to 移回 from。
- 目标已存在、跨盘符、目录非空等冲突在 dry-run 阶段就报出来，不等到执行一半。
- 目标路径仍走 `classify_path`（越界要授权）。

### 价值

`delete_paths` 已经有 90% 的基础设施（审批门、路径分类、审计、回收站错误码翻译），
这个工具是同一条链的正向版本。**性价比最高的一项。**

预估 1–2 天。

## 建议 2：提醒的自然语言入口（`remind`）

### 缺口

`schedule_cron` 要求 5 段 cron 表达式：

```json
{"cron": "0 15 * * 3", "prompt": "..."}
```

个人助手的典型用法是「**周三下午三点提醒我交周报**」。让模型自己把这句话翻译成
cron 是可以的，但：

- 时区/夏令时/跨月边界容易错；
- 用户看到的确认文案是 `0 15 * * 3`，无法验证；
- 一次性提醒用完还在表里（cron 是周期语义）。

### 做法

```
remind(when: "2026-11-04 15:00" | "in 2h" | "tomorrow 9am", text: str)
```

- 内部解析成一次性任务（`schedule_once` 语义），走既有的 cron 表 + `notify` +
  飞书投递，只是 `repeats=1`，触发后自动清理。
- 确认文案回给人看的是**人性化时间**（"11 月 4 日 15:00"），不是 cron 串。
- 绝对时间优先；相对时间用当前本地时间算，落盘时存绝对值——避免进程重启后
  相对基准漂移。
- 复用已有的空闲门控（`idle_after_s`）与投递语义（outbox + ack）。

### 价值

把"个人助手"最核心的一个用法补齐，且**几乎不新增基础设施**——cron 表、
notifier、飞书投递、审计都已就位，缺的是一个解析函数和一次性任务语义。

预估 1 天。

## 建议 3：使用统计视图（`/usage`）

### 缺口

token、工具调用、会话时长都落在事件流里（`usage` 事件、`tool_started`、
`turn_completed`），但**没有任何聚合视图**。用户问"我这周花了多少"、
"哪个工具用得最多"、"哪类会话最费 token"，只能自己 grep jsonl。

### 做法

`/usage [days]` + 飞书卡片，聚合：

| 维度 | 数据源 |
|---|---|
| token（输入/输出/缓存命中） | `usage` 事件 |
| 每回合耗时 p50/p90 | `turn_started`/`turn_completed` |
| 工具调用次数与失败率 | `tool_started`/`tool_completed` |
| 审批次数与被拒次数 | 审计事件 |
| 记忆写入/召回命中 | 审计事件 |

实现上复用 `audit.collect()` 的单遍扫描与文件预算（已经做过性能优化，
37ms）。

### 价值

**这直接服务于"记忆/RSI 到底有没有用"这个问题**——有了使用统计，才谈得上
"用了几周后看趋势"。成本低（纯聚合，无新数据源），但让所有其他机制变得可评估。

预估 1 天。

## 建议 4：跨工作区的「我在哪见过这个」搜索

### 缺口

`grep`/`glob`/`ls` 都接受 `path`，但默认工作区。用户常见的问题是：

- "上次那份文档放哪了"
- "我记得有个文件提到 X，但不确定在哪个项目"

现在模型得挨个猜路径，或者用户自己说清楚。`find_sessions` 只搜会话，不搜文件。

### 做法

不是加一个"全盘扫描"工具（性能与隐私都不可控），而是：

- 一个**已登记工作区**的联合搜索：`grep` 增加 `scope: "workspaces"` 选项，
  并发扫 `WORKSPACE_ROOTS` 里登记的几个目录，带总预算（文件数/耗时上限）。
- 命中结果按工作区分组返回，每条带路径。
- **跳过**秘密文件、`.git`、`.cache`、`node_modules`（复用既有忽略规则）。

### 价值

中。它提高的是"找回信息"的效率，但需要用户先把工作区登记好（`/workspace add`）。
如果用户根本不用多工作区，这项价值接近零——**建议先观察是否有这个需求**。

预估 1 天，但建议最后做。

## 建议 5：日历 / 邮件（不建议现在做）

### 缺口

个人助手最经典的两项：日程、邮件。我们都没有。

### 为什么建议不做

| 成本 | 说明 |
|---|---|
| OAuth 全流程 | 授权、刷新、撤销、多账号，每家 provider 不同 |
| 数据驻留 | 邮件正文进上下文 = 把整个收件箱暴露给模型，与"最小可见"原则冲突 |
| 注入面 | 邮件是最典型的 prompt injection 载体（Muse 专门为它做了一次性验证码过滤、密码重置链接过滤） |
| 维护 | API 变更、限流、配额，都是长期负担 |

Muse 的邮件连接器要**同时**做确定性过滤 + 分类器模型才敢开，那是另一个量级的工程。

**替代方案**：如果真有需求，用 MCP 接第三方（现有 MCP 桥已支持），把成本和
风险留在外部；我们只保证"第三方工具默认要审批"这一条。

## 优先级建议

| 顺序 | 项 | 预估 | 理由 |
|---|---|---|---|
| 1 | `move_paths` + 撤销 | 1–2 天 | 补保护等级倒挂，复用 delete 的 90% 设施 |
| 2 | `remind` 自然语言 | 1 天 | 个人助手核心用法，几乎零新设施 |
| 3 | `/usage` 聚合 | 1 天 | 让所有机制变得可评估，数据都已有 |
| 4 | 跨工作区搜索 | 1 天 | 先观察是否真有需求 |
| — | 日历/邮件 | 不做 | 建议用 MCP 接 |

**三项合计 3–4 天**，都不新增外部依赖、不改变安全模型，且都复用既有基础设施。

---

## 与"验证价值"那条线的关系

必须有先后：**先做建议 3（`/usage`），再用它来判断其他功能值不值得做。**

现在的困境是：记忆、主动性、RSI 都做了，但**没有任何数据说它们有用**。
`/usage` 是把"机制存在"变成"机制有效"的最小前提——它能回答"记忆召回命中率
多少"、"主动性建议被采纳几次"、"自改进真的降低了什么"。

否则会陷入"不断加机制、永远无法判断"的循环。
