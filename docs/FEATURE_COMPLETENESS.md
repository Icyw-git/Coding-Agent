## 二、这一轮补上的三个"看不见"

三个功能都"能用"，但**用户看不到、也查不到**——这类缺口比 bug 更容易长期存活，因为
没有任何测试会失败。

### 1. 主动性档位不在 `/status` 里

`HARNESS_PROACTIVE_MODE` 有三档（`off` / `observe` / `auto`），是唯一"会自己开口"的能力。
但 `/status` 里一行都没有：

- 设了 `observe` 的人不知道它是不是在记录；
- 设成 `off`（默认）也发现不了，会以为"它怎么从来不给建议"。

现在：

```
已启用：主动建议：观察模式（只记录，不打扰）
未启用：…、主动建议（设 HARNESS_PROACTIVE_MODE=observe|auto）
```

未启用时连"怎么开"一起说——那一刻用户最需要的恰恰是它。

### 2. 11 个开关没有文档

代码里 88 个 `HARNESS_*`，11 个在 `ENVIRONMENT.md` 里查不到。其中 5 个是**用户可配**的：

| 开关 | 为什么重要 |
| --- | --- |
| `HARNESS_PROACTIVE_MODE` | 主动性的唯一入口（三档） |
| `HARNESS_KEEP_RECENT_TOKENS` | 压缩保留多少现场 |
| `HARNESS_TOOL_DISCOVERY` | 工具按需发现（默认关，见性能文档） |
| `HARNESS_VERIFIER_GUARD` | 硬拒改测试的开关（只排查时关） |
| `HARNESS_API_LOG_BACKUPS` | 日志保留份数 |

另外 6 个是 worker 的内部传参（`HARNESS_SCREEN_*` / `HARNESS_OCR_*`），也补了说明，
免得有人以为要手填。

**守卫**：`test_every_switch_is_documented` —— 代码里出现而文档里没有就红。

### 3. `/status` 里有一段重复注释

`status_report.py` 里同一句四行注释写了两遍（复制粘贴残留）。已删。

## 四、判"好用"的标准（自查表）

一项功能算"好用"，要同时满足：

1. **有入口**：TUI 命令 / 工具 / API 里能用（`/suggest`、`tool_search` 都算）；
2. **看得见**：`/status` 或对应界面能确认它当前的状态（这次补的就是这一条）；
3. **查得到**：相关的 `HARNESS_*` 在 `ENVIRONMENT.md` 里有说明（有守卫）；
4. **有守卫**：改坏了会有测试红（不是靠人记得）；
5. **失败可解释**：出错时说清"为什么"和"下一步"，而不是抛原始异常。

按这五条回扫，**只有四条曾经不满足**：`/status` 缺三处、文档缺 11 个开关。
都已修，并加了守卫。

## 五、不建议再"优化"的地方

三个看起来该做、但评估后不做的：

1. **工具延迟加载默认开**：缓存净亏（第 92 节），已默认关闭；
2. **截屏复用常驻 worker**：省 1.4s，但要重写 150 行 PS，而它历史上一共被调用 1 次；
3. **扩展 `SEARCH_IGNORE` / 尊重 `.gitignore`**：都改语义（前者把某个项目的目录名写进
   通用规则，后者会让"搜被忽略的目录"失效），不是修 bug。

**性能优化的另一半是证明某件事不值得做**（第 95 节）。
