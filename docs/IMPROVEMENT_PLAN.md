日期：2026-11-01。承接 [DEEPSEEK_SUPERAGENT_RESEARCH.md](DEEPSEEK_SUPERAGENT_RESEARCH.md)

**这份文档解决什么问题**：把"我们还剩哪些问题"和"要吸收哪些做法"排成一个**有依赖顺序、
每步都可验收**的计划，而不是一张想做就做的愿望清单。

**三条硬约束**（贯穿全篇）：

1. **先写测试，再写代码。** 每个修复都必须先有一个**会失败的测试**；写不出失败测试的，
   先写一个能复现的脚本（并在 PR 描述里贴输出）。没有复现的"修复"一律不做。
2. **先修现有问题，再补新能力。** P0 全部完成并全量绿之后，才动 P1。
3. **不扩大影响面。** 每项改动只碰它必须碰的文件；跨模块的"顺手重构"单独成项，不混进修复。

## 2. 执行纪律（怎么写、怎么验）

### 2.1 测试先行的三种形态

| 情形 | 先写什么 | 例 |
| --- | --- | --- |
| 纯 Python 逻辑 | 失败的单测 | B5/B6/B8/B9/B10/B12：断言文案/结构 |
| 需要真实环境的行为 | 失败的单测（注入假实现）+ 一个真机脚本 | B1/B2/B3：`scripts/profile_desktop.py` + `.test-tmp/phase1/*.ps1` |
| 只能人判断的 | 验收清单条目（写进 `FEISHU_ACCEPTANCE.md`） | B16 |

### 2.2 每项完成的定义（DoD）

1. 有一个**先失败、后通过**的测试（或脚本 + 贴出的前后输出）；
2. `ruff check` 干净；
3. 全量 `pytest` 绿（**一次只跑一遍**，避免上轮那种"跑太多次把进程耗尽"的假警报）；
4. 若改变了任何用户/模型可见文案，同步 `docs/` 里引用该文案的地方；
5. `DEBUG_LOG.md` 记一节：现象、证据、改法、教训（一段话即可）；
6. 提交信息写清"问题 → 证据 → 改法"，不写"顺手优化"。

### 2.3 一次只动一类东西

一个提交里只做一件事：修文案就只修文案，抽函数就只抽函数（行为不变，测试不改断言）。
这样出问题时能一眼定位。

## 3. P0 清账（先做，做完才进 P1）

顺序按"影响 × 成本"排，箭头表示依赖。

### P0-1 让 `wait(absent)` 的返回值不再说谎（B3）

**问题**：`matched=True` 的含义是"已确认"，但截断/读不到时也返回它。

**方案**（两选一，取 A）：

- **A（推荐，最小）**：回包增加 `confirmed: boolean`，`matched` 只表示"目标状态成立"；
  工具层文案按 `confirmed` 分流（已有），并在**未确认时把 `matched` 也置为 false**，
  只保留 `observedAbsent` 明细。
- B：未确认就继续轮询到 deadline（会让大窗口的 absent 永远超时，体验更差）。

**测试先行**：
- 单测：截断结果 → `matched is False` 且文案含"没再出现"；
- 单测：完整遍历 → `matched is True`，文案含"已消失"；
- 真机脚本：`HARNESS_DESKTOP_TREE_NODES=5` 强制截断，断言 `matched=False`。

**验收**：真机两态输出与单测一致；`WaitResult` 的 docstring 说清两个字段的区别。

**影响面**：`desktop_control_windows.WaitResult`、`desktop_scripts.Wait-ForControl`、
`tool_desktop._wait_control_text`、`tests/test_desktop_wait.py`。

### P0-2 大控件量窗口的遍历（B1 + B2，先测量再决定）

**问题**：预算超 3 倍；且该窗口稳定只返回 2 个控件。

**方案分两步，不合并**：

1. **先定位**（不计入改动）：用 `scripts/profile_desktop.py walk` 与 `.test-tmp/phase1/probe_*.ps1`
   在 200 子控件窗口上分段计时（`FromHandle` / `FindAll` / 每节点 `Read-ElementNode`）。
   **限时 30 分钟**：
   - 定位到"单个 `FindAll` 不可中断"→ 走 2a；
   - 定位到"某类节点的 pattern 探测是跨进程调用且很慢"→ 走 2b；
   - 30 分钟内定位不到 → **停在文档记录**，并把 B1 降级为"已知限制"（写进
     `DESKTOP_CONTROL_RESEARCH.md` 的最坏情况表），不在没搞清之前动核心遍历。
2. **2a**：把"一次 `FindAll(Children)`"改成"逐个 `GetFirstChild`/`GetNextSibling`
   的显式循环，每处理一个子节点检查一次预算"。**必须先证明不退化**：
   `profile_desktop.py walk` 在 Chrome / Edge / Terminal 上的中位耗时不得高于现状 +20%，
   否则放弃（这是他们文档里写死的取舍：`FindAll` 是他们快的原因）。
3. **2b**：只在探测到慢 pattern 时延迟探测（先出行，再补 `operations`），或对已知慢类型跳过探测。

**测试先行**：
- 结构测试：遍历实现里"每处理一个子节点检查预算"（按函数名锚定，别用字符串位置）；
- 回归基线：`profile_desktop.py walk` 的输出存档前后对比（人看，不做断言）。

## 5. 两个需要先决策的问题

### 5.1 B7：工具输出到底用哪种语言

现状是分层不一致：

| 族 | 语言 |
| --- | --- |
| `desktop_*`、`screen_*`、审批卡、TUI/飞书 | 中文 |
| `clipboard_*`、`files`、`patch`、`exec`、`search` | 英文 + `Error:` 前缀 |

**决策**（建议）：**按"这一族是否面向人"划界**，并把规则写死：

- **面向人**（审批卡、TUI、飞书、桌面/屏幕工具的输出）→ 中文 + 全角标点；
- **纯数据通道**（搜索/读取/执行的原始内容）→ 保持原样，只保证**标记词**一致
  （`(truncated: ...)`、`(no matches)`），并把这条写成规则。

理由：这两族服务不同读者；混着改会制造第三种不一致（这也是前几轮我得出的结论）。
**动作**：只在文档里定规则 + 在 `tests/test_ui_copy.py` 的 docstring 里引用它，不改代码。

### 5.2 B2 是否值得为它改核心遍历

只有当 §3 的 P0-2 定位出可复现的根因、且改法不使常见应用变慢时才做。
否则**接受现状**，并把"大列表类窗口可能只列出少量控件"写进工具输出的兜底文案
（已在第 65 节做过一部分）。

## 6. P1 吸收调研的可迁移机制（清账完成后）

每项都按同一模板写：借鉴点 → 我们的落点 → 测试先行 → 验收 → 代价。

### P1-1 主动性加一档 `observe`（借鉴 accept mode）——**被 B18 阻塞**

> **先解决 B18**：这个模块目前没有调用方。在死代码上加"档位"只会让假信心更厚。
> 先决定接线还是删除（建议接线：一个 `/suggest` 命令 + 手动触发即可验价值），
> 再谈 observe/auto 的模式划分。

- **借鉴点**：默认"评估但只记录 would-accept"，而不是"不评估"。
- **落点**：`src/proactive.py`。新增配置 `HARNESS_PROACTIVE_MODE=off|observe|auto`（默认 `off`，
  保持现状）；`observe` 写一条 `would` 记录（含触发规则、建议、为什么没执行），不产生任何工具调用。
- **测试先行**：`off` 不评估；`observe` 评估但不调用工具、且台账出现 `would`；`auto` 与现状一致。
  三条都是单测（现有 `tests/test_proactive.py` 已有假模型注入点）。
- **验收**：三种模式的台账可区分；`/usage` 或 `/status` 能显示当前模式。
- **代价**：小。`preference`：`decision` 仍由代码算，不让模型写。

### P1-2 授权记录"依据"，依据变了就失效（借鉴 Mandate + Policy 版本）

- **借鉴点**：授权不是"勾选有效期"，而是"基于某条依据的一次判断"；依据变了要重新判断。
- **落点**：`src/approval_scope.py` + `src/audit.py` 台账。给每条放行记
  `basis = {rule_version, tool_class, target, policy_hash}`；恢复/重放（会话续跑、定时任务复用
  凭据）时比对 `policy_hash` 与 `target`，不一致则要求重新批准。
- **测试先行**：同一条 bash 命令，白名单哈希变了 → 需重新审批；未变 → 免审批照旧；
  目标域名变了 → 需重新审批。三条单测。
- **代价**：中。要在台账写入处统一 `basis`（`grant_ledger` 已存在，扩展字段即可）。

### P1-3 判官逐项留痕（阴性也要写）

- **借鉴点**：`rule_assessments` 必须对每条启用规则给 `matched`，缺项即 schema 错误。
- **落点**：`src/approval.py` 的 LLM 审查官。要求返回 `checks: [{code, matched, reason}]`，
  代码校验"覆盖所有启用的判断项"，缺项按"审查失败"处理（回到人工审批）。
- **测试先行**：缺项 → 视为不可用、走人工；全 false → 放行/拒绝按现有规则；
  含未知 code → 拒绝并记审计。三条单测。
- **代价**：小（schema + 校验），风险：模型多写几个字段，token 略增。

### P1-4 给人预留一个槽位（借鉴 WorkerSlots）

- **借鉴点**：人触发的唤醒可以用"额外 1 个"并发额度，且优先拿空槽。
- **落点**：任务/子代理调度（`src/limit*.py` / `src/background_task.py`）。规则：
  `origin='person'` 的唤醒在满额时仍可 +1；新任务不得占用该额度。
- **测试先行**：满额时人唤醒成功、新任务排队；人唤醒结束后额度自动收回。两条单测。
- **代价**：小。

### P1-5 后台转交按角色定阈值（借鉴 5s / 60s）

- **借鉴点**：主循环 5 秒转后台、子代理 60 秒，比按关键词猜稳。
- **落点**：`src/background_task.should_run_background`。保留关键词启发式作为"未知角色"的兜底。
- **测试先行**：主循环下 6 秒命令转后台；子代理下 6 秒不转、61 秒转。两条单测。
- **代价**：小。风险：把原来"看起来慢"但确需前台的命令转走（用现有 `run_in_background=false` 覆盖）。

### P1-6 覆盖文本记录基准版本（借鉴 prompt 版本）

- **借鉴点**：用户改过的内置文本记录"基于哪一版"，默认文本更新时提示 diff。
- **落点**：本项目目前没有"可覆盖 prompt"（我们改的是仓库里的 md）。**若引入**，最小形态：
  `HARNESS_HOME/prompts/<part>.md` 覆盖 `prompts/` 内置版本，文件头写
  `based-on: <内置文件的 sha1>`；启动时比对，不一致就在 `/status` 提示"默认已更新"。
- **测试先行**：覆盖文件 + 基准 sha 不符 → `/status` 出现提示；相符 → 不提示；
  覆盖文件缺 `based-on` → 视为用户自定义、不提示。
- **代价**：中。**优先级最低**，因为它服务的是"长期演化"，我们还没到那一步。

## 9. 明确不做（防止这份计划自己膨胀）

| 不做 | 理由 |
| --- | --- |
| 引入 9 张表的事件溯源（trigger/disposition/effect/outbox） | 我们规模（单机会话 + 台账）用不上；复杂度上一个量级（详见调研 §9） |
| 每工单一个目录 + `prepare` 命令 | 我们是"一人一机"，`create_worktree` 按需即可 |
| 主会话禁 `sleep` / 禁长前台命令 | 适合"纯路由会话"，我们是交互式主循环 |
| 把 P0-2 做成"可中断遍历"而不先证明不退化 | 常见应用的遍历速度是核心体验，不能为罕见窗口牺牲 |
| 统一全仓中文化（B7 的"全改"方案） | 会制造第三种不一致；只定规则、不改代码 |
