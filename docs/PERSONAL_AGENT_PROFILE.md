# Personal Agent 前置 Profile（速度 / 缓存 / 内存）

日期：2026-10-24。目的：在开始 [PERSONAL_AGENT_PLAN.md](PERSONAL_AGENT_PLAN.md) 阶段 0 之前，
记录当前基线，供后续对比。全部为本机实测；没有向 provider 发起新请求。

## 1. 采样环境与口径

- 解释器：`D:/Anaconda_envs/envs/aitest01_py310/python.exe`（CPython 3.10.20），Windows。
- 数据：`.cache/sessions` 51 个会话（9.3 MB）、678 次模型调用、21 个记忆文件（93 KB）。
  最大会话 4.9 MB / 846 事件 / 239 条重建消息；第二大 1.0 MB / 783 条消息。
- 计时为单机 wall clock；内存同时用 `tracemalloc`（Python 分配峰值）和进程 RSS
  （Windows `K32GetProcessMemoryInfo`）。重复 3–5 次取中位数；UI 挂载每个配置单独进程，
  避免模块缓存和冷启动互相污染。
- 复现：
  - `python scripts/profile_conversation.py`（provider 用量、缓存命中、缺失阶段计时）
  - `python scripts/profile_turn_pipeline.py [--limit full]`（本地回合流水线，无网络）
  - `python scripts/profile_storage.py --session largest`（会话读写内存）
  - `python scripts/bench_ui.py 10000 100 100`、`python scripts/bench_layout.py 5000 100`
  - `python scripts/bench_history.py 1000`（已修复：原先引用了已迁走的 `HISTORY_INITIAL_MESSAGES`）

## 2. 对话速度

### 2.1 provider 侧：本轮无法测量

历史 678 次调用全部缺少 `request_ms` / `ttfb_ms` / `stream_ms`（`profiled_calls = 0`），
说明这些字段落盘之后还没有新的成功请求。此前真实采样返回 `402 Insufficient Balance`
（请求 ID `5fe035f1-a236-44b6-865f-200b95398b74`），本轮按约定没有重试、也没有伪造数据。
因此**端到端延迟与首 token 时间暂无有效基线**；provider 恢复后用新 session 采集，再补这一节。

### 2.2 本地回合流水线（每次模型请求前）

`scripts/profile_turn_pipeline.py`，`local` 记忆召回，5 次中位数：

| 会话 | 消息 | 重建历史 | 记忆召回 | context/system | 压缩预处理 | 请求拼装 | 稳态合计 |
|---|---|---|---|---|---|---|---|
| 239 条（有 usage） | 239 | 6.1–6.5 ms（冷启动 342–368 ms） | 18.8–21.5 ms | 1.6–2.0 ms | 21.8–22.4 ms | 0.7 ms | **43–46 ms** |
| 783 条（无 usage） | 783 | 17.9–21.9 ms（冷启动 61–78 ms） | 18.2–23.9 ms | 1.5–2.0 ms | 88.5–103.3 ms | 0.7–0.9 ms | **126–130 ms** |

多次重复运行波动约 ±10%；同一台机器上其他负载会影响绝对值，趋势稳定。

### 2.2b 优化后复测（同机、同一数据）

本轮落地的两项优化（`estimate_size` C 层计数 + 记忆解析缓存）之后：

| 会话 | 记忆召回 | 压缩预处理 | 稳态合计 | 降幅 |
|---|---|---|---|---|
| 239 条 | **2.1 ms**（原 18.8–21.5） | **3.2 ms**（原 21.8–22.4） | **7.3–8.6 ms**（原 43–46） | 约 5–6× |
| 783 条 | **4.4 ms**（原 18.2–23.9） | **13.9 ms**（原 88.5–103.3） | **21.8–23.6 ms**（原 126–130） | 约 5× |

重建历史不变（6.1–17.2 ms），因为它是纯 JSON 解析 + 投影，不是本轮优化目标。
注意上述合并不包含 `rebuild_openai_history`（`AgentRuntime` 每回合一次，6–20 ms）。

关键差异在压缩判据：`agent_loop` 稳态用上一次 `usage.prompt` 作为 `size`，只估增量；
`size=None` 时（首轮、直接调用、以及**没有 usage 事件的旧会话**）每轮都要对全量历史
逐字符 `estimate_size`。同一 783 条会话强制 `--limit full` 时为 93.7 ms，与上表一致。
cProfile 显示 `estimate_size` 占压缩阶段绝大部分，5 次调用约 160 万次字符迭代。

结论：本地固定开销约 **50–130 ms/回合**，相对模型延迟可以忽略；但“无 usage 会话”会在
每轮多做一次全量估算，属于长会话的可观测成本。

### 2.3 会话读取与列表

- `AgentRuntime.list_sessions`（51 个会话）：冷 143.5 ms，随后中位 **2.3 ms**（命中
  size/mtime 摘要缓存）。watcher 轮询状态、飞书 `/sessions` 不会因反复扫描而线性变慢。
- 最大会话 `read_events()`：92.5 ms，`tracemalloc` 峰值 **24.0 MB**；改用
  `rebuild_openai_history()`：362.8 ms，峰值 **1.9 MB**。即“长会话内存换 CPU”的既有取舍。
- TUI 打开会话（真实历史，100×30，独立进程冷启动）：
  - 239 条：分页 200 → 1.30–1.33 s；全量 239 → 1.32–1.41 s（消息数差异不足以体现分页收益）。
  - 783 条：分页 200 → 0.60–0.66 s / 894 行；全量 783 → 1.70–1.81 s / 4348 行。
  - 两者内容字符数接近（99k vs 113k），说明挂载耗时跟渲染块数量/内容复杂度强相关，
    而不是单纯消息条数。**分页在 200 条以内基本无差别，783 条起约省 1.1 s。**

## 3. 缓存

### 3.1 provider prompt cache（历史 678 次调用）

- 加权命中率 **89.6%**（33.85M prompt tokens，30.34M cached）；逐调用中位 **97.8%**，
  均值 91.6%；低于 50% 的调用 29 次。
- 分布：100% 命中 0 次；90–100% 544 次；75–90% 69 次；50–75% 23 次；25–50% 6 次；
  0–25% 20 次。即绝大多数回合吃满缓存，少数冷启动/失效调用拉低均值。
- 会话内首次调用 16 次：中位 92.5%，均值 76.5%（其中 2 次 0 命中）。
- 与间隔的关系（样本小，仅记录）：<30 s 的 591 次调用中位 97.8%、14 次低于 50%；
  ≥30 min 的 5 次调用中位 50%、均值 51%。没有观察到明确的 TTL 悬崖，但长间隔样本不足。
- 归因字段：190 次调用带 `system_fp` / `tools_fp`，同一会话内**没有任何 system/tools/model
  变更**，因此这 26 次低命中不是提示前缀（system/工具表/模型）变化造成的。
- `history_snipped` 之后的 210 次调用中位 98.8%，没有出现预期中的前缀断裂；说明截断发生的
  位置与后续命中区域不冲突，或供应商缓存粒度更粗。
- `cache_prefix_status` 诊断 0 次（默认关闭）。**阶段 0 若要做缓存回归，需要显式开启
  `HARNESS_DEBUG_CACHE=1`（可用 `HARNESS_DEBUG_CACHE_SAMPLE=N` 抽样），否则只能看到
  命中率、看不到前缀是追加还是重写。** 239 条会话实测每次诊断约 2.3 ms；采样目前
  默认 1（全采样），长会话建议设 5–10。

### 3.2 本地缓存

- 会话摘要缓存：冷 143.5 ms → 热 2.3 ms（见 2.3）。
- 事件/历史投影缓存上限 2 MB（`HARNESS_EVENT_CACHE_MAX_BYTES`）：最大会话超出后按需重读，
  所以长会话 `rebuild` 冷启动 361 ms、热 6 ms。
- 记忆文件解析：本轮已加 `(size, mtime_ns)` 级 frontmatter/正文缓存，每轮召回从
  18–24 ms 降到 2–6 ms；写入路径主动失效，外部修改靠 mtime 兜底。

结论：当前内存压力主要来自 TUI 进程与长会话渲染（约 60–70 MB RSS），单回合执行本身增量很小；
会话缓存路径（24 MB 峰值）只在显式 `read_events()` 时出现。常驻 daemon 的内存基线可按
“解释器 + harness ≈ 26 MB，加 API 栈和会话活动后另计”估算，仍需真实 daemon 采样确认。

## 5. 对方案的直接影响

1. **全局单回合协调**不会带来可感知的性能损失：本地固定开销优化后只有 7–24 ms/回合，
   远小于模型调用。
2. **watcher 轮询成本可接受**：会话列表热路径 2.3 ms，SSE 只拉增量；真正的成本在飞书发送，
   不在本地扫描。
3. **缓存监控已有采样开关**：`HARNESS_DEBUG_CACHE=1`（+ `HARNESS_DEBUG_CACHE_SAMPLE=N`）；
   阶段 0 的缓存回归可直接用，注意长会话每次诊断约 2–7 ms。
4. **长会话打开时间**在 783 条时从 1.7 s 降到 0.6 s，分页策略有效；200 条以内无差别。
5. **没有 usage 事件的会话**原本每轮多付一次全量估算（783 条约 +80 ms）；本轮
   `estimate_size` 优化后已降到约 14 ms，不再是瓶颈。
